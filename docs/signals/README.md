# 观察期（Observation Window）

> **观察期只做一件事：记录信号。不修、不重构、不抽象、不分析。**

## 时间

| | |
|---|---|
| 启动 | **2026-09-19**（V3.1 合并后立即开始） |
| 4 周上限 | **2026-10-17** |
| 状态 | 进行中（窗口开启，尚未达到退出条件） |

## 退出条件（V3.1 M4 冻结）

```text
固定退出：4 周上限（2026-10-17）

提前退出（满足任一）：
  A. ≥3 个相同结构问题（同一 Cluster 至少 3 个信号）
  B. ≥5 个 S1/S2 信号
  C. 出现需要新增 Contract 的候选问题，且已有 ≥2 个独立信号支撑

"C" 的严谨性来自最后半句：单个信号也可能是噪声，必须 ≥2 个独立信号支撑，
防止单点噪声打断冷却期。
```

## 只做什么

- ✅ 把信号写进 `docs/signals/NNNN.md`（照 `TEMPLATE.md`）
- ✅ 记录触发场景 / 期望 / 实际 / 复现 / 严重程度 / 架构影响初判

## 不做什么

- ❌ 不修 / 不重构 / 不抽象 / 不做预防性设计
- ❌ 不写"如果…就…"
- ❌ 不统计分类 / 不做趋势判断 / 不做任何形式的分析
- ❌ 不写 Cluster hint

为什么这么严：**一旦允许"分类"，观察期会退化成分析期；一旦允许"趋势判断"，
分析会退化成设计；一旦允许"设计"，冷却期的意义就消失了。**

## 每周只做三件事

1. 数信号数量
2. 数 S1/S2 数量
3. 记录日期

## S1 例外

S1（无法完成用户任务）**只在阻塞时**触发记录，不因为"看起来严重"而提前升级处理；
观察期内一律只记录。
