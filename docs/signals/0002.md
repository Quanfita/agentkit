# Signal 0002

- **Date**: 2026-09-19
- **Trigger**: 为验收消息序列契约，用手工构造 / 改写过的含 `assistant(tool_calls)` 历史直接调用
  DeepSeek `deepseek-flash`（`OpenAIModel.generate()` 与裸 `AsyncOpenAI` 两条路径都试过）。
- **Expected**: 只要序列满足 I1–I5（结构合法），Provider 就该接受 —— 这正是"内部序列契约 + Adapter 承担
  Provider 差异"的分工设想。
- **Actual**: 被拒，且**报错指向一个 Kernel Message ABI 里根本不存在的字段**：
  `400 The 'reasoning_content' in the thinking mode must be passed back to the API.`
  单变量矩阵（同一份被服务端接受过的载荷逐项突变，共 16 次真实调用）：

  | 载荷 | 结果 |
  |---|---|
  | P1 逐字节重放（原始 id + 原始参数） | **接受** |
  | M0 / M1（去掉 system）/ M3（换 tool content）/ M4（不喂 tools）/ M6（assistant 加文本） | **接受** |
  | P3（改 user 内容为同义句） | **接受** |
  | P4 / P6（在 assistant **之前**插入 user 消息） | **接受** |
  | 跨进程、数分钟后逐字节重放 ×3 | **接受** |
  | M2 仅改 `tool_call.id`（其余逐字节相同） | **拒绝**（reasoning_content） |
  | ① 换成同 key 在**另一次 run** 里生成过的 id（并改参数） | **拒绝**（reasoning_content） |
  | P2 / P5（在 assistant 之前插入消息，使 assistant 相邻） | **拒绝**（reasoning_content） |
  | Q1 / Q3（连续两条**纯文本** assistant，无 tool_calls） | **拒绝**（reasoning_content） |
  | Q2（`[system, user, assistant(tc), tool, assistant(text)]`，末尾 assistant 为手工构造） | **拒绝**（reasoning_content） |
  | M5 / ④（声明 2 个 tool_call 只回 1 个结果） | **拒绝**（结构性错误：insufficient tool messages） |

  **关键对照（真实任务，不是手工载荷）**：真机跑一个需要 ≥2 轮工具的任务，
  3 次请求全部**接受**，形状依次为
  `[system,user]` → `[system,user,assistant(tc),tool]` → `[system,user,assistant(tc),tool,assistant(tc),tool]`，
  `reason=FINAL`，模型正确报出 `VALUE=42`。
  即：**AgentKit 的真实多轮流程不受影响；受影响的是被手工构造/改写/迁移的 assistant 消息。**
- **Reproduction**:
  ```bash
  python - <<'PY'
  import asyncio, os, copy
  from openai import AsyncOpenAI
  SYS = {"role": "system", "content": "You are a coding agent."}
  U   = {"role": "user", "content": "列出当前目录里的文件"}
  A   = {"role": "assistant", "content": None, "tool_calls": [{"id": "call_00_sRcx79nrFTawvle9twHB5352",
         "type": "function", "function": {"name": "list_dir", "arguments": "{\"path\": \".\"}"}}]}
  T   = {"role": "tool", "content": "a.txt", "tool_call_id": "call_00_sRcx79nrFTawvle9twHB5352"}
  TOOLS = [{"type": "function", "function": {"name": "list_dir", "description": "list",
            "parameters": {"type": "object", "properties": {"path": {"type": "string"}}, "required": ["path"]}}}]
  async def main():
      c = AsyncOpenAI(base_url="https://api.deepseek.com", api_key=os.environ["DEEPSEEK_API_KEY"])
      async def go(label, msgs):
          try:
              await c.chat.completions.create(model="deepseek-flash", messages=msgs, tools=TOOLS)
              print(f"{label}: 接受")
          except Exception as e:
              print(f"{label}: 拒绝 → {str(e)[:95].splitlines()[-1][:95]}")
      # 先跑一次真实 run 取得 id，再逐项突变（id 必须在同一次真实 run 的响应里拿到）
      await go("P1 逐字节", [SYS, U, A, T])
      a2 = copy.deepcopy(A); a2["tool_calls"][0]["id"] = "call_A"
      t2 = copy.deepcopy(T); t2["tool_call_id"] = "call_A"
      await go("M2 仅改 tool_call.id", [SYS, U, a2, t2])
      await go("Q1 连续两条纯文本 assistant",
               [SYS, U, {"role":"assistant","content":"A"}, {"role":"assistant","content":"B"}])
  asyncio.run(main())
  PY
  ```
  （`P1` 接受的前提是这条 assistant 消息确实由服务端在本次会话中生成过；
  换一个从未生成过的 id 或改一个字节即落到 `M2` 那一行。）
- **Severity**:
    - [ ] S1 = 无法完成用户任务
    - [ ] S2 = 完成了但方式意外
    - [x] S3 = 完成但体验不佳（真实多轮任务 3/3 请求全部成功；
      受影响的是"改写/合成/迁移 assistant 消息"的场景：报错指向 ABI 不存在的字段，定位成本高）
- **Architectural implication**:
    - 现有三个防线（Firewall / ABI Freeze / Conformance）能否拦住？
        Firewall 无关；ABI Freeze 冻结的是形状，而这里的差异是 Provider 语义；
        Conformance 6 台设备全走真实 loop 路径，因此 6/6 全绿却完全没有覆盖这一类载荷。
    - 拦不住的，它落在哪一层？
        - [ ] Kernel（罕见）
        - [ ] Runtime / Harness
        - [x] Context / Executor / Provider
        - [ ] 实现 bug
    - 初步判断（不做归类，只描述现象）：现象与 `context/contracts/message_protocol.md` 的定位一致 ——
      Provider 语义差异落在 Adapter；但 `reasoning_content` 在 Kernel `Message`
      （`role / content / tool_calls / tool_call_id`）里没有可承载的位置。
      逐字节重放被接受、改一个 id 即被拒，指向"服务端对自己生成过的响应有识别/缓存"，
      该机制未继续隔离（窗口内不做分析）。
      未测：**丢弃前缀**（真实截断）后的载荷是否仍被接受 —— 已测的是"插入消息"与"改 user 内容"。
